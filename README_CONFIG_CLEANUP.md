# 🎯 配置參數清理方案總結

## 📌 核心理念

> **不是簡單地刪除代碼，而是系統性地識別、驗證和安全移除**

您發現的問題：

- ✅ AI Agent 生成了很多參數
- ✅ 許多參數在不同情景下定義
- ✅ 但大部分參數從未被使用
- ✅ 導致代碼臃腫和維護困難

```
┌─────────────────────────────────────────────────────────────┐
```

## 📋 使用流程

### 第 1 天：分析和診斷

```bash
# 1. 執行自動分析工具
node analyze-config-usage.js

# 2. 查看生成的報告
cat config-usage-report.json | less
# 或用 Excel 打開 CSV 版本

# 3. 記錄待清理清單
# 複製 "未使用的配置" 部分
```

**輸出**：

- 所有導出配置的使用情況
- 未使用配置的完整清單
- 每個配置的首次使用位置

### 第 2 天：人工審查

**對每個未使用的配置進行驗證**：

```
對於每個配置：
  □ 執行二次搜尋（確保結果準確）
  □ 查看代碼註釋（是否有說明用途）
  □ 查詢 git 歷史（何時添加、為什麼）
  □ 詢問團隊（是否有人知道用途）
  □ 確認決策（刪除或保留）
```

**分類結果**：

- ✅ 確認可刪除：TRAFFIC_LIGHT_CONFIG、VEHICLE_EXIT_CONFIG 等
- ⚠️ 可能有用：保留做為備份註解
- 🔒 必須保留：核心配置（ANIMATION_CONFIG、COLLISION_CONFIG 等）

### 第 3-7 天：逐步清理

**採用分組清理策略**：

```
第 3 天：清理組 1
  ├─ TRAFFIC_LIGHT_CONFIG   ✅ 已移除
  ├─ VEHICLE_EXIT_CONFIG    ✅ 已移除
  └─ 測試驗證 ✅ 通過

第 4 天：清理組 2
  ├─ EASING（如果真的未使用）
  ├─ PUSH_FORCE（如果真的未使用）
  └─ 測試驗證

... 依此類推
```

**每次清理的步驟**：

1. 創建備份註解
2. 刪除配置定義
3. 更新 default export
4. 重新啟動 npm run dev
5. 進行完整功能測試
6. 確認控制台無誤

### 第 8 天：最終驗證

```bash
# 1. 執行最終分析
node analyze-config-usage.js

# 2. 確認已移除的配置不再出現

# 3. 進行完整功能測試
npm run dev
# 測試所有主要功能

# 4. 記錄最終統計
# 移除前後的代碼行數對比
```

## 🔑 關鍵要點

### ✅ 該做的事

1. **使用自動化工具** - 避免手工漏檢
2. **保留備份註解** - 記錄原始值方便復原
3. **分組進行** - 每次刪除幾個相關參數
4. **每次都測試** - 確保沒有隱藏依賴
5. **記錄變更** - 便於日後追蹤和回溯

### ❌ 不該做的事

1. **批量刪除** - 無法確定哪個刪除導致問題
2. **直接刪除** - 丟失原始定義和移除原因
3. **只相信搜尋** - 可能有字符串動態訪問
4. **跳過測試** - 風險很高
5. **遺忘更新導出** - 導致編譯錯誤

## 📞 需要幫助？

### 常見問題

**Q: 分析工具沒有輸出怎麼辦？**
A:

1. 確認 Node.js 已安裝 (`node --version`)
2. 確認在項目根目錄執行
3. 檢查 src/classes/config 目錄是否存在

**Q: 搜尋結果有誤怎麼辦？**
A:

1. 檢查備選拼寫方式
2. 查詢 git 歷史確認原始用途
3. 手動查看配置文件和使用地點

**Q: 刪除後發現出錯怎麼辦？**
A:

1. 立即 git revert
2. 查看備份註解恢復原始值
3. 重新分析是否有漏掉的引用
